\chapter{Future Work}
\label{chap:Future_Work}

While the results of our proposed methodology and tooling are promising, there are limitations. We needed constraints to manage the scope of work for a PhD thesis and for technical reasons. Although the CyclicL tool is self-contained in terms of features and requirements, there is currently no modelling environment for the \gls{UCD} and goal diagram explained in the methodology. As a result, there is no supported traceability between the \gls{UCD} and the goal diagram, the feature model, or the requirement canvases. This makes comprehensive traceability from requirements through features to their sources difficult. It also leaves a gap in iterative change analysis, because there are currently no facilities for change-impact analysis between feature modelling and the \gls{UCD}. As users learn more about their product, we anticipate and encourage them to iterate through the various phases of development in this methodology, and we want to support that computationally as well.

Using this methodology to support the development of safety and security assurance cases is another avenue we would like to explore. Because the methodology emphasizes traceability, it may support the development of assurance cases. This possibility partly explains the design decision to include the \texttt{Safety} type of requirement in the \tool\ metamodel. It would include traceability to the eventual modelling environments for \gls{UCD}s and goal diagrams in \tool.

Another interesting avenue of research for the PACEMAKER requirements was explored by Wang et al.~\cite{wang2012identification}, which examines the assumptions made in the PACEMAKER requirements document~\cite{scientific2007pacemaker}. A potential avenue for future work would be to integrate the analysis process for identifying assumptions in system requirements with the \tool\ methodology, enabling traceability to those assumptions. This would help ensure that assumptions made during development are identified, documented, and traceable throughout the product lifecycle.

%This presents another challenge of traceability and justification. It requires the engineer to be aware of the links between the domain and problem space analysis and the feature and requirement models in the tool. This implicit knowledge will eventually need to be documented somewhere to support future development changes and safety-critical development assurance. As a result, one potential path is to create a bridge between domain analysis modelling and the current tool to extend traceability to the concept phase of development. While we expect \gls{UCD} and goal diagrams to remain mostly static once they are created, the direct traceability could be helpful documentation for onboarding new employees to help them get familiar with why certain decisions were made, support change impact analysis justifications, and aid the development of an assurance case by having complete end-to-end traceability between the problem space and the solution space.

The implementation of the tool for \tool\ is still incomplete, as we have only demonstrated the minimum viable product's capabilities. We still need to add many functions to make the tool more complete. There are currently no constraints in the tool to ensure that all user-created models are valid according to the metamodel. While the tool offers flexibility, there is room for stronger validation to provide more robust analysis support for users creating models. It is, after all, a trade-off between flexibility and error checking.

We are currently relying on conventions and good engineering to create semantically meaningful models, but maintaining them at scale within a company or industry is very difficult. Another avenue of development would be to allow users to create these models both textually and graphically. Very often, adoptability of a tool, especially an \gls{MDE} tool, is difficult because many engineers are unfamiliar with \gls{MDE} techniques and approaches. Creating a textual environment for these models may improve the usability and approachability of CyclicL for industry use. Next, we would want to implement consistency checking within the tool. This would remove much of the burden from the engineer to ensure that their features and requirements are consistent across features. This is a unique challenge, as the requirements are specified using the Gherkin behavioural approach and may require us to re-evaluate the specification language we implement within the requirement canvases of CyclicL.

Other future work tasks mentioned throughout this thesis include integration with existing test compilers, integration with previous feature modelling tools, and general UI enhancements. Because there are many Gherkin test environments, building an integration bridge with \tool\ would help with verification tracking and traceability. Integration with another feature modelling tool, such as FeatureIDE, would provide a basis for exploring the impact of the feature-requirement hierarchy defined in this thesis on existing feature weaving and composition techniques. Finally, as mentioned in the evaluation section, industry and user validation, scalability testing, and quantitative and qualitative comparisons against existing technologies remain as future work for continued analysis of \tool\ as both a methodology and a tool.
