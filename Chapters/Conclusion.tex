\chapter{Conclusion}
\label{chap:Conclusion}

What comes first, the requirement or the feature? In this thesis, we have attempted to outline an answer to this question. Incidentally, and perhaps unsurprisingly, the answer is both, and it depends. Both realities are possibilities for companies in industry as they start new product development from scratch or try to reuse previous work for a new model. So we support both of them. 

The ultimate answer, however, is neither. The stakeholder use cases and goals come first as we conduct a domain analysis and problem space exploration. We have shown that, by following Meyer's requirements engineering approach, we can leverage both informal and formal \gls{MDE} techniques to perform domain and problem space analysis. We found that goal diagrams were an easy-to-use, informal approach to capturing knowledge of what stakeholders really want to do, which helped inform why they would want to use the product we developed. The \gls{UCD} was important for establishing how they would use our product. Identifying what interfaces the stakeholders would need from the product to accomplish their goals. Goal diagrams and \gls{UCD}s formed the core of our informal modelling techniques for domain analysis and problem space exploration.

Feature modelling and our requirement canvas leveraged more formal approaches to modelling and problem space exploration; with \ tool, we could enforce syntactic and semantic rules when creating the models. Equating features and use cases also helped to establish requirements for our features as we refined the use cases into user stories. With our proposed feature-requirement hierarchy, those requirements are immediately scoped and owned by the features, making an easy transition from problem space exploration to requirement specification. We have demonstrated both formal and informal approaches to domain analysis, problem space exploration, and requirement development while using \gls{MDE} techniques. We have explored several processes for accomplishing these tasks in multiple environments. Finally, we have demonstrated how this methodology can be used to identify gaps in existing documentation and how to improve requirements specification and identification. Thus, we conclude that we have satisfied~\ref{RQ4}

Thus, we have shown satisfaction of~\ref{RQ4}.

\gls{FDD} is a well-established development strategy. A major contribution of this thesis is the proposed feature-requirement hierarchy, which establishes that features own their requirements. Another contribution is our equating of use cases from \gls{UCD}s to features in \gls{PLE}. Our methodology refines use cases into user stories to define requirements for each. Because the use cases and features are aligned, those requirements also apply to the feature. When combined with the proposed feature-requirement hierarchy, we end up with well-defined requirements for each feature. An added bonus we discovered was a natural ordering that emerged in the requirements, driven by the use of user stories as a refinement process. These all contribute to well-defined, scoped features and potentially aid project planning by providing an implied ordering of requirements from the user stories. This implies a natural decomposition in the requirements as well, as they are scoped by the features that own them. Overall, there is a much clearer path to specifying features in a \gls{FDD} environment, supported by the methodology and tool. This satisfies~\ref{RQ1}.

One of the main contributions of our methodology is the encapsulation of feature requirements. By defining this hierarchy, we have shown how it facilitates traceability between features and requirements. We also removed ambiguity in the relationship between features and requirements. We have demonstrated how this hierarchy enables greater traceability granularity through our implementation of CyclicL. We were able to define a formal metamodel to capture this hierarchy and implement a tool to show satisfiability of this proposal. Through CyclicL, we demonstrated the benefit of this hierarchical relationship between features and requirements in semi-automated maintenance and generation of traceability matrices. This was completed as a by-product of following the methodology and naturally using \tool\ to create models and specify our requirements. We thus got the traceability matrices without any manual intervention or extra steps in the engineering process. We conclude that this reduces much of the time and effort that would traditionally have been spent manually creating or maintaining engineering data traceability, satisfying~\ref{RQ2}.

Finally, CyclicL has demonstrated the potential benefits of a self-contained \gls{PLE} tool that embeds requirements, in the context of iterative and incremental development. We have shown that CyclicL can support incremental development of both feature and requirement models. By leveraging \gls{EMF} and Sirius, we demonstrated the possibilities enabled by a tool that maintains traceability across both requirement and product changes, without reliance on external support. While the current tool still has limitations in supporting iterative changes, we have demonstrated how future development can continue to address these shortcomings. Due to the current limitations in the tool, we conclude that we have partially satisfied~\ref{RQ3} with \tool\ as a tool that supports iterative and incremental traceability development in parallel with feature and requirement development. We give it a partial designation as there are still limitations on how \tool\ can support iterative changes under our current definition of a change between development phases.

Overall, our methodology has demonstrated improvements in an existing requirement document, identified avenues for potential improvements in requirement engineering and feature modelling, and shown potential for integration with existing development practices. Our contributions include the following:

\begin{itemize}
	\item The integration of automated traceability with domain space exploration, feature modelling, and requirement engineering.
	\item The definition of a clear hierarchy between features and requirements.
	\item A tool supported approach enabling incremental and iterative development of feature models and requirements.
	\item A unified workflow between various \gls{MDE} and \gls{PLE} techniques for feature modelling and requirement engineering.
\end{itemize}

\tool\ and its supporting methodology are ripe for further exploration and continued development to support safety-critical development in further domains and potentially as a more generalized approach to requirement engineering across industries.
