\chapter{Implementation}
\label{chap:Implementation}

In the previous chapter, we explored a methodology for leveraging common points between \gls{PLE} and \gls{MDE} for domain analysis, requirement engineering, and feature modelling. We have also introduced a language, \tool, to demonstrate how requirement modelling can be combined with feature modelling to improve traceability via a defined hierarchy between features and requirements.

In this chapter, we explore an implementation of \tool\ that demonstrates the tool's support for the language. Through this implementation, we aim to demonstrate the capability of automatic traceability generation and maintenance from good modelling practice, and the feasibility of iterative and incremental development using the proposed methodology with tool support.

As a proof of concept, we have implemented a \gls{DSL} using Sirius~\cite{viyovic2014sirius} and Xtext~\cite{eysholdt2010xtext} to show the feasibility of automated traceability between features and requirements. This is a core component of the methodology, as we require the means to specify feature models and requirements to capture their interrelationships to enable automated traceability. By implementing a \gls{DSL}, we can enforce syntactic and semantic rules defined by the metamodel to create verifiable models that support incremental, iterative development.

The tool for \tool\ also provides an environment in which we have explored potential composition strategies. We anticipate that, as a result of designing the language of \tool\ to focus on feature-requirement traceability, there may be some side effects. By implementing the language in a tool, we can explore some of these side effects, such as the impact it may have on composition techniques from \gls{PLE}. Some modifications may be required as a result of the relationship we have introduced between features and requirements. 

%Though not automated at this time, the facilities in \tool\ were sufficient as a proof of concept to allow further development for composition in the future.

\section{Implementation Objectives}

\subsection{Goals and Limitations}

In Figure~\ref{fig:CyclicL_goals} we capture some anticipated goals for our end-users. In conjunction with our own objectives, we use these to support our high-level requirements for \tool. At the time of writing, the scope of \tool\ is focused only on the traceability portion of the methodology; we have scoped user goals for inclusion after they complete an independent domain analysis. We assume that users will complete the other steps of this methodology (goal diagrams, \gls{UCD}) using other means prior to or as part of an iterative process when using \tool. This is a limitation of \tool\ for now, as we do not currently support modelling or traceability from the domain analysis to the identified features and requirements. We strongly encourage users to complete the prior steps of domain analysis before modelling the features and requirements, as it helps the development process build a better conceptual model and understanding of the intended product~\cite{kang1990feature}.

\begin{figure}
	\centering
	\includesvg[width=\textwidth]{CyclicL_goals}
	\caption{Anticipated goals of users for \tool.}
	\label{fig:CyclicL_goals}
\end{figure}

We have several key goals we aim to achieve by implementing a tool for \tool. 

\begin{itemize}
	\item Enforce syntax and semantic rules of \tool\ when creating models.
	\item Explore impacts of traceability generation and maintenance when creating and changing models within the tool.
	\item Enforce automated traceability as a side effect of model creation.
	\item Explore the impact of feature-requirement traceability on both feature modelling and requirement modelling.
	\item Reuse as many specifications and definitions from previous work as possible.
\end{itemize}

We expect the main users of the tool to be engineers, but not limited to software engineers. To be successful, the tool needs to allow users to create feature models to define product families. It also needs to have a way to define requirements. Since \tool\ is also an implementation of the methodology, it must also implement the relationship we have defined between features and requirements. Since we want to support iterative and incremental development, the tool for \tool\ also needs a way to enhance the generation and maintenance of traceability matrices for requirements and features. Finally, the implementation needs to be robust to change, supporting future changes such as traceability to use cases and goals, and automated processes such as change impact analysis and product composition.

Based on our objectives, the tool for \tool\ has two main modelling environments that are distinct and connected, as demonstrated in the abstract syntax in figures~\ref{fig:feature_mm}, \ref{fig:req_canvas_mm1}, and~\ref{fig:req_canvas_mm2}. The first is the feature modelling half of the tool. The purpose of this modelling environment is to allow the user to build a product family, describing their features and how they are related. The second modelling environment is the requirement canvas. This portion of the tool enables users to specify their requirements, associate requirements to design elements, and assign reviewers and test cases to requirements. This is where traceability is captured between the feature and various requirements aspects. 

Another objective we had during development was reuse. As we explored and implemented traceability in the spirit of \gls{PLE}, we sought to identify as many reusable aspects as possible from previous specifications and tool implementations. Thus, \tool\ is also inspired by FeatureIDE~\cite{kastner2009featureide, thum2014featureide} and GEARS~\cite{GEARS} for their abstract and concrete syntaxes. This prevented us from having to reinvent how to build a feature modelling tool so we could focus more efforts on the requirement canvas and the traceability matrices.

\subsection{Requirements}
We extracted high-level requirements from previous work on building a product line and on a coffee cup to guide initial development plans for \tool~\cite{10.1145/3652620.3688349}. We also aim to support iterative and incremental development life cycles. We generally define an iterative change as one based on feedback from later stages of development or from stakeholders. These are usually larger changes that may arise while cycling between phases of development. In the context of \tool, we want to generate and maintain traceability between features and requirements as users iterate between feature modelling and requirement modelling. Examples of iterative change include a new version of a development artifact or its redesign. Incremental changes are usually smaller in scope and bound within a single development phase, such as feature modelling \textit{or} requirement modelling. Examples of incremental changes include refactoring, updating a definition, or changing a connection between components. While we have been using these definitions to guide our development philosophy, they may not be shared by others. This may present a challenge to the adoption or usage of \tool. Therefore, we included ease of use and adoption as another goal. Our initial list of requirements was as follows:

%relative to an incremental change. 

\begin{itemize}
	\item Tool shall provide the user with an environment for defining requirements.
	\item Tool shall provide the user with an environment for defining features.
	\item Tool shall allow the user to specify design elements.
	\item Tool shall allow the user to relate one or more requirements to one or more design elements.
	\item The tool shall allow the user to use features to capture and own requirements (ownership in this context refers to a compositional relationship between features and requirements, where features are composed of requirements).
	\item Tool shall automatically create and maintain a traceability matrix.
	\item The tool shall facilitate the iterative development of the requirements canvases (\textit{note:} this remains ongoing work).
	\item The tool shall facilitate the incremental development of the requirements canvases.
	\item The tool shall aim to promote familiarity and ease of use to increase adoption rates.
\end{itemize}

Along with these requirements, we also use the prior specifications for encapsulating feature requirements. We treat the requirements encapsulated by a feature as attributes and consider them feature requirements, thus scoped by the feature. As the exploration of requirement modelling started with the requirement diagrams from SysML, we reused as much as possible from the original specification. We then focused more on traceability and integration with feature modelling, diverging from the original specification until we arrived at what we now refer to as our requirement canvas. For a rough idea of what we wanted the requirement canvases to look like, we sketched requirements for a disposable coffee cup with a handle, shown in Figure \ref{fig:CoffeCup_ReqModel}.

\section{Abstract Syntax}
\label{sec:Abstract_Syntax}

The metamodel shown in Figure~\ref{fig:metamodel} served as the specification for building the tool for \tool. The abstract syntax can be roughly divided into two main parts: the feature model shown in Figure~\ref{fig:feature_mm} and the requirement canvas shown in Figures~\ref {fig:req_canvas_mm1} and~\ref{fig:req_canvas_mm2}. This aligns with our requirements for \tool. The requirement canvas portion of the metamodel is not a complete implementation of the SysML specification for requirement diagrams. The SysML specification served as a source of inspiration for the requirement canvas created in the tool for \tool. \tool\ has a greater emphasis on traceability and requirement specification that is not explicitly captured in SysML. Similarly, we have gone a step further by specifying different types of requirements in our implementation, a detail not captured in the original SysML specification. We therefore drew heavily on the SysML requirement diagram specification, but did not limit ourselves to faithfully implementing it in our requirement canvas. This is why we refer to the requirement modelling portion of the tool as a requirement canvas rather than a requirement diagram. This captures our deviation from the SysML specification. 

\subsection{Feature-Requirement Encapsulation}
To enable features to encapsulate requirements, the \texttt{FeatureEntity} class inherits from the \texttt{Requirement\_Canvas} class. This implementation is what allows the features to encapsulate the requirements. We chose the inheritance relationship because it allows features to share the semantics of a requirement canvas while also allowing us to define a feature independently of a requirement canvas syntactically. Using another relationship for implementation, such as a composition relationship, would have introduced a strict ownership semantics that we did not find added value, and instead would have added an extra layer of abstraction between features and requirements, cluttering the traceability with useless information. Through this inheritance relationship, the features own the requirements directly without any abstraction. Further, the inheritance specification forces a 1-1 relationship between requirements and features, meaning that every new set of requirements requires a new feature to be encapsulated, reinforcing the convention of a unique feature per unique set of requirements. This relationship is highlighted in Figure~\ref{fig:requirement_feature_inheritance}.

\subsection{Feature Model Specification}

The feature modelling specification of the tool is loosely inspired by the formal approach from Peter H\"{o}fner \textit{et al.} ~ \ cite {hofner2006feature,hofner2011algebra}, with a small extension to account for requirement encapsulation. We use this specification rather than creating a new one to leverage prior proofs and work on formal specifications for feature modelling. It saved us time and let us begin development much sooner. We consider the relationship between features and requirements within a product family as shown in Figure~\ref{fig:spec}. Using this definition, we treat each feature as a set of requirements, where each requirement within the feature is unique. As stated in the definition, however, it does not account for duplicate requirements in separate feature elements. This will be addressed in future iterations. 

Specifying the hierarchy between features and requirements, both in a metamodel and using a set-theoretic approach, provides a better understanding of the mechanisms that link the two entities. The idea is that this will help specify and implement mechanical processes, for example, change impact analysis in the future using a formalized language like the Object Constraint Language (OCL)~\cite{richters2002ocl, cabot2012object}, or another formal approach. This should help validate the mechanism and streamline development, as we can use one of its derivatives, such as \gls{EVL} or \gls{AQL}, baked into Eclipse.

\begin{figure}
	\begin{align}
		\text{Let } \mathbb{F} \text{ be a set of arbitrary elements that we call features.}\\
		\text{We can call a collection (set) of features a product.}\\
		\text{The set of all possible products is } \mathbb{P} \overset{\mathrm{def}}{=} \mathcal{P}(\mathbb{F})\\
		\text{A collection of products (an element of } \mathcal{P}(\mathbb{P})\text{)}\\
		\text{is called a product line (or product family)}\\
		\text{This model does not capture feature duplication}\\
		\text{Let } \mathbb{R} \text{ be a set of arbitrary elements that we call requirements.}\\
		\text{We can call a collection (set) of requirements a feature.}\\
		\text{The set of all possible features is: } \mathbb{F} \overset{\mathrm{def}}{=} \mathcal{P}(\mathbb{R})\\
		\text{This model does not capture requirement duplication.}
	\end{align}
	\caption{Definition of the relationship between features and requirements.}
	\label{fig:spec}
\end{figure}

There are three defined relationships for features: mandatory, alternative, and optional. These are specified with bidirectional references to allow visibility in either direction from any feature. This decision was made to enhance traceability in the modelling environment and simplify development of the traceability matrices. The multiplicities are also defined with 0..1 at the top end to limit how the feature composition will work. This limits the number of nodes a leaf element can be connected to, constraining the models that can be built and simplifying feature composition. We also highlight the requirement set owned by the null feature based on the composition relationship from \texttt{RMDL\_Project} to \texttt{Requirement\_Canvas}. The justification for this structure is to provide an extra space for requirement specification that can later be refined by cutting and pasting the  requirements into a canvas encapsulated by a proper feature. To prevent instantiated projects from being cluttered with too many disconnected drawing spaces, we limit the multiplicity to [0..1].

\subsection{Requirement Canvas Specification}

The requirement canvas portion of \tool\ was inspired by SysML requirement diagrams~\cite {sysml2019omg}; however, we did not implement it according to its original specification. The main reason for the divergence was our focus on implementing the feature-requirement hierarchy and specifically on developing for feature-requirement traceability. As a result, we decided to iterate on requirement diagrams as a means of exploration for traceability and requirement specification, leading to the inception of the requirement canvas. During exploration, we made several decisions at both the requirements and design levels for \tool\ that led to its current state at the time of writing. This includes the classifications for functional and non-functional requirements, the graphical syntax implemented, and the specification language embedded in the model. We explain these differences in the following passages.

Next, for the requirements in the requirement canvas, we identified four requirement categories: \texttt{Functional}, \texttt{Qualitative}, \texttt{Constraint}, and \texttt{Safety}. These are shown in Figure~\ref{fig:req_type}.

\begin{figure}[hbt!]
	\centering
	\includegraphics[width=\textwidth]{req_type.png}
	\caption{Specification for the 4 requirement types in \tool.}
	\label{fig:req_type}
\end{figure}

Functional requirements follow their traditional definition: things that a product or system must do. Qualitative requirements are those that affect how a product or system accomplishes its function. These include the look, feel, and usability, as well as humanity and some performance requirements that are not categorized as functional. Constraint requirements are those that impose limitations of some type on a product or system. These include operational, environmental, maintainability, support, security, cultural, political, and legal requirements. These requirement definitions can be found in Robertson Volere requirements~\cite{robertson2000volere}. We found a benefit for more specific categories beyond just non-functional requirements, as it lets the user be more intentional with their specification. We find this especially beneficial for identifying safety requirements separate from the other traditional non-functional requirements. The safety requirement category is critical for our purposes, as it identifies all requirements related to the safety of users or stakeholders involved in the function of a product or system. We highlight safety requirements as a separate category to target \tool\ towards safety-critical development. It is important to note that requirement categorization relies heavily on system or \tool feature scoping. For example, we hypothesize that in a safety feature, a safety requirement may be considered a functional requirement due to the feature scope. A functional feature, however, may contain safety requirements that differ distinctly from its functional requirements. This distinction relies heavily on the engineer creating the model and the model's context.

The effect of having these classifications front and center for the end user is that it forces them to consciously decide what kind of requirement they are creating at the time of development. Anecdotally, we have noticed minimal emphasis on the type of requirement identified. The process of determining the type of the requirement is often treated as tech debt, or is assumed by default to be a functional requirement. In this way, the end user may still assume that the requirement is a functional requirement; however, that detail is now explicitly part of the requirement specification, rather than left to interpretation at the head of the user and left up to interpretation by others during development, until the requirement type is explicitly decided.

We also added three more classes besides the requirements: \texttt{DesignElement}, \texttt{Review}, and \texttt{TestCase}, shown in Figure~\ref{fig:design_test_review}. 

\begin{figure}[hbt!]
	\centering
	\includegraphics[width=\textwidth]{design_test_review.png}
	\caption{Specification for design, test, and review in \tool.}
	\label{fig:design_test_review}
\end{figure}

The test case and review classes are for verification and validation bookkeeping, respectively. We also have an enum \texttt{TestType}. This enum allows users to categorize the tests users may want to apply to their requirements. At this time in development, only \texttt{UnitTest} is implemented as a type, but more can be added in future revisions. This is also one of the reasons why we include design elements within the requirement canvas. The test cases are meant to determine if a requirement has been verified against its traced design elements, while the review represents whether the requirement has been validated. Currently, verification and validation are expected to occur outside \tool\ because they are out of scope for initial development. Design elements are also meant to be black boxes as we do not want to pollute our requirement environment with design aspects. We have limited it to determining if a design element is hardware, software, or neither (undetermined when building the requirements or an integrated system). Another reason for including design elements in the requirement canvas is to provide an opportunity for future development of design generation based on the requirements specified in \tool.

\section{Concrete Syntax}
\label{sec:Concrete_Syntax}

The design decisions for developing the concrete syntax for the requirement canvas follow the ideas from the Physics of Notation~\cite{5353439}. Various colours and shapes were used to maintain a bijective relationship between the concrete syntax and intended semantics. For example, in Figure~\ref{fig:concrete_syntax_req_diag}, all of the requirements have the same shape to show they have commonality as they inherit from the \texttt{Requirement} type, but use different colours to differentiate themselves from each other. Similarly, \texttt{Test Cases} and \texttt{Reviews} are dynamically coloured to indicate whether they pass/fail and are approved/unapproved, respectively. Finally, the \texttt{Design Element} symbols dynamically change colour if they are stereotyped as software, hardware, or black-boxed.

\begin{figure*}[hbt!]
	\centering
	\includegraphics[scale=0.043]{Figures/Requirement Diagram_SteeringWheel.jpg}
	\caption{An example of the concrete syntax for the requirement canvas using requirements from the automotive domain.}
	\label{fig:concrete_syntax_req_diag}
\end{figure*}

For the feature modelling portion of \tool, we attempted to maintain a syntax as close to traditional as possible. This was to satisfy the ease-of-use and familiarity requirements. Maintaining the original syntax for feature modelling to the best of our ability during implementation should provide some intuitive familiarity to users familiar with feature modelling, while allowing a new user to learn relatively easily by leveraging previous work and documentation about \gls{PLE}. Given Sirius's default limitations, there are still differences. 

Figure~\ref{fig:concrete_syntax_feat_mod} shows an example product family created in \tool. The model's root is shown in the grey box, and the model's features are shown in white circles. The mandatory reference uses an arrow and a black diamond at the target to represent the AND relationship. The optional relationship uses a circle with a plus at the target to represent OR relationships. The alternative reference uses an arrow and a white diamond at the target to represent XOR relationships. In a top-down modelling layout, the reference source is at the top, and the reference target is at the bottom. We aimed to maintain a syntax as similar as possible to feature modelling conventions and to maintain a bijective relationship between the syntax and semantics.

\begin{figure}[hbt!]
	\centering
	\includegraphics[width=\textwidth]{feature_model_acc.png}
	\caption{An example of the concrete syntax for the feature model using features for an adaptive cruise control system from the automotive domain.}
	\label{fig:concrete_syntax_feat_mod}
\end{figure}

Along with the graphical portion of \tool, we also implemented an Xtext-based~\cite{eysholdt2010xtext} specification language. The implemented specification language is based on the Gherkin specification language~\cite{nicieja2017writing, cucumberdocs}. We chose this as the specification language for our requirements for a few reasons. Gherkin uses a structured natural language for specifications, thus making it relatively approachable for users when defining their requirements. Further, despite using natural language, it employs keywords to provide a predicate-logic structure to the specifications. The keyword `Given' is used for preconditions, `When' is used for events, and `Then' is used for postconditions. The combined approach of adding predicate structure to natural language makes it relatively easy to specify requirements and to implement the language within \tool. This helps satisfy the ease-of-use and adoption requirement, as it makes the tool more approachable to learn and implement in a development process. We found that Gherkin struck a nice balance between formal and informal approaches to specification, aligning with Meyer's requirement style, which inspired some of this methodology.

\begin{figure}
	\begin{lstlisting}
		Given{
			Precond FeatureExists: "Steering wheel has heating feature."
			Precond CarIsOn: "Vehicle is on."
		}
		When{
			Event UserTurnsOnHeating: "User interacts with heating interface to turn on/off wheel heating."
		}
		Then{
			Postcond StateChange: "Wheel heating boolean changes state to on or off depending on current state."
		}
	\end{lstlisting}
	\caption{Gherkin specification for Wheel Heating on/off functional requirement. The high-level requirement description is: User shall be able to turn wheel heating on/off.}
	\label{fig:specification}
\end{figure}

An example of what the concrete syntax is for the traceability matrices is shown in figure~\ref{fig:feature-requirement-trace-spec}. This is a feature-requirement traceability matrix. The requirements are all in the first column. Subsequent elements in each row are directly traceable to the requirements via the relationships specified in the metamodel and are accessed via AQL queries. For example, to get the \texttt{Requirement ID} value, we use the query \texttt{aql:self.ID}. Since each row is each row is focused around the requirement in the first column, the only way to display anything in the traceability matrix is to have the model elements some how be traceable to the requirement via any of the relationships defined in the metamodel in appendix~\ref{apdx:CyclicL_mm}.

\begin{sidewaysfigure}

The design decisions of what to show in the traceability matrices are to show as much information as possible about the element from the first column. It is possible that some information may be removed in the future or new types of traceability matrices will be identified as needed. In the example from figure~\ref{fig:feature-requirement-trace-spec}, this also includes the feature that owns the requirement to ensure we capture the hierarchical relationship in the matrix based on the same specification used for the modelling.

\section{Design Decisions}

A major design decision for \tool\ was using our own implementation for feature modelling. Other tools such as FeatureIDE already exist and are native to Eclipse. We decided to use our own implementation to avoid constraints imposed by an existing tool, so we can focus on the traceability aspects of the tool. Another reason was to allow us some flexibility in implementing the new hierarchical relationship between features and requirements. Further, this gave us the flexibility to explore how we might navigate the created models and traceability matrices.

Another major design decision was diverging from the requirement diagrams of SysML to the requirement canvas. This was done to emphasize traceability of requirements and features as a primary function for this methodology and reinforce it in the implementation of the tool. Due to the time and scope of this thesis, the Goal Diagram and Use Case diagram were not included in the tool implementation of CyclicL.

We decided to rely on the majority of syntactic options available in Sirius for domain specific modelling development. This was both to speed up development and reduce the potential cost of restarting development, which we did several times as we iterated on the tool implementation. This is also true for the traceability matrices that are generated based on the models.

\subsection{Composition Implementations}

The relationship between features and requirements makes traditional composition techniques for \gls{PLE} a challenge. Given our convention that a variant requirement necessitates a new feature, the path to composing features and requirements to a product is relatively straightforward at this time. Currently, the approach focuses on the features themselves in the composition, assuming each feature has unique requirements. If a requirement applies to multiple features, it should be abstracted up a level in the tree to a higher feature. This currently reduces cross-cutting concerns and dependencies between requirements. This allows users to define the constraints and rules governing how the features within a model can compose into a product (e.g., every car needs 4 wheels). More complex analysis is planned for future work; however, as a proof-of-concept, \tool\ has the facilities to support such development. With the \texttt{Product\_Variant} class in the metamodel~\ref{fig:metamodel}, we provide the facilities for a user to manually create instances of their product. Also, because of the composition relationship we use, all product instances are owned by the feature model in which they are created. The inheritance relationship also means they don't need to be new semantic elements to represent the various features and requirements across product variants. We can leverage model slicing to create those new variants and instances. Naturally, the inheritance also allows all the traceability mechanisms to apply to the product variants the same way they do to the parent feature model.

\section{Summary}
In summary, the tool for \tool\ has shown promise for enforcing the syntax and semantics we desire. We implemented the concrete syntax while maintaining a bijective relationship between the metamodel definitions and the concrete syntax in the tool. Our design decisions were justified, and we satisfied the tool objectives we outlined before beginning development.
